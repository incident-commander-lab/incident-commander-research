01 — The real DevOps problem

The Problem Is Not Lack of Telemetry

Incident — checkout / payment path is slow and erroring

The observability stack has already fired. The engineer can already see:

database latencyIncreased — database looks guilty
CPUIncreased — app looks saturated
network / timeoutsPresent — path looks guilty
deploymentLanded ~10 minutes ago — change looks guilty
downstream / siblingAlso erroring — dependency looks guilty

H1 Database overload

Pool exhaustion, lock storm, or storage saturation cascading into 5xx.

H2 Faulty deployment

The recent release or config change introduced the fault.

H3 Network issue

Timeouts and retries are the cause, not a symptom.

H4 Downstream dependency

An upstream/downstream neighbour failed first and cascaded.

The engineer now has evidence, but still has to decide what to investigate next. All four stories still fit this first screen.

Why Investigation Efficiency Matters

Where time actually goes

Detection is often fast. Investigation is where responders jump between Grafana, logs, traces, deploy history, and runbooks, testing one explanation after another while the service is still failing.

The expensive pattern is not “no data.” It is checking evidence that both remaining stories would survive — or locking onto the first plausible story (usually the recent deploy).

Operational consequences

EffectWhy it happens
Longer time to diagnosisLow-value checks first; discriminating signal later
Cognitive overloadContext split across tools and tabs
Repeated investigationSame dashboards revisited without a decision rule
Premature conclusionNearby deploy looks causal and gets rolled back
Wrong mitigationInnocent change reverted; real cause still live

We do not claim a measured MTTR percentage. We claim investigation under residual uncertainty is a real, costly step in the chain above.

Not our job

  • Replace metrics, logs, traces, or APM
  • Claim commercial RCA “does not work”
  • Output one unexplained root cause and stop
  • Auto-change production

Our job

  • Keep competing explanations explicit
  • Attach evidence to each explanation
  • When they still overlap, pick the next check they disagree about
  • Update beliefs from that result, then repeat
Our focus is not replacing observability or RCA. Our focus is selecting the next investigation step that is most useful for reducing uncertainty between plausible explanations.

05 — Solution

Our Approach: Evidence-Guided Investigation

Iterative loop — not Input → AI → Answer. Observe → Reason → Investigate → Update → Reason again.

1–3 Context

1. Ingest incident evidence

2. Build incident context (alert, change, topology, priors)

3. Maintain competing hypotheses in prototype: seeded in the case

4–6 Decision

4. Evaluate evidence against each hypothesis

5. Identify residual uncertainty (close posteriors / rollback at stake)

6. Select next investigation step from disagreement, not from “what is reddest”

7–9 Update

7. Collect that evidence (probe)

8. Update confidence; eliminate if contradicted

9. Recommend diagnosis / action — engineer decides

Conceptual product

A general investigation assistant over live telemetry.

What this repository is

A working policy engine + console over recorded incident bundles, so the loop is reproducible and demoable.

06 — How the system thinks

Hypothesis-Driven Investigation

It does not pick the current leader and stop

Even if H1 is 40% and H2 is 35%, acting on H1 can be wrong. The useful question is which available check would change those numbers.

H1 Database — illustrative 40%

Predicts: connection wait leads; sibling service stays healthy.

H2 Deployment — illustrative 35%

Predicts: only this service fails; wait is a lagging symptom.

H3 Network — illustrative 25%

Predicts: traces show path loss independent of deploy/DB.

Prototype decision scoring — implemented in ic/probe.py

Not a claim of optimal information theory. A transparent heuristic:

divergence(observable) = # distinct predictions
among surviving hypotheses

info_gain(probe) = max divergence it measures

select = argmax( info_gain / cost_ms )

A1 Inspect DB connection wait — H1 vs H2 disagree → gain > 0 → selected.

A2 Re-read CPU — both already consistent with CPU↑ → gain 0 → skipped.

A3 Heavy trace dump — may be down-weighted if load_class is heavy.

VoI panel also shows eig − λ·cost − μ·risk for the engineer. In this build, probe selection uses the rule above.

Percentages on the left are an illustrative teaching example. Live numbers come from softmax over lens scores, clamped to 94% max.

Say: Heart of the project: distinguish, do not crown the current leader. Then read the formula so a judge who opens probe.py is not surprised. Judge: Heuristic, inspectable, not a fake theorem.
07 — User workflow

How a DevOps Engineer Uses the System

AI = investigation assistant

  1. Incident is already detected in the existing stack
  2. Engineer opens the investigation workspace
  3. System loads current evidence (prior fan-out)
  4. Competing hypotheses and supporting refs are shown
  5. If still close, system proposes the next check and why
  6. Check is run against the case; result is attached and hashed
  7. Confidence updates; a hypothesis may be eliminated with a reason
  8. Diagnosis + rollback recommendation — not an auto-rollback

Human = decision owner

Recommend a probeSilently change traffic
Recommend rollbackExecute rollback

11 — Strongest technical slide

From “What Is the Cause?” to “What Should I Check Next?”

State

Uncertainty: H1 vs H2 still inside τ=0.15, or leader implies rollback.

Catalog: P_conn_wait (wait time), P_inv_errors (inventory errors).

Already visible: CPU, 5xx, deploy diff, inventory p99 blip — none of these is allowed to be the hidden discriminator (authoring invariant).

Prototype scoring — actual

Usefulness ≈ do surviving hyps predict different labels?

Relevance ≈ probe.measures ∩ predicted_observations

Cost ≈ authored cost_ms (not live load)

Risk ≈ 0 for observations; constant for gated intervention display

P_conn_wait: divergence 2 / 410ms

P_inv_errors: divergence 0 → skipped

Next best action

Inspect connection-wait (P_conn_wait)

Why: H1 says wait leads; H2 says wait lags. One cheap histogram falsifies one story.

Why not inventory errors: they do not split the two predictions, so they cannot reduce this uncertainty.

We do not claim an optimal information-theoretic policy. We claim a working, inspectable scoring rule whose ablation we can show: hide this check, and the hard cases are not resolved from prior evidence alone.

15 — Practical value

Where This Helps the Incident Responder

Designed to reduce unnecessary exploration

Prefer the check that splits remaining stories over another dashboard that both stories already survive.

Evidence-driven reasoning

Every score cites refs. Elimination prints predicted vs observed. Verdict can be sealed and verified later.

Lower cognitive load

Hypotheses, evidence, next step, and trail in one workspace instead of five browser tabs.

Human-in-the-loop

The engineer owns mitigation. The system does not autonomously roll back or shift traffic in this build.

More consistent investigation

Targets on-call variance: the discriminating question does not depend only on who remembers the runbook.

Reusable paths — partial today

History lens matches runbook/prior-incident keywords. A real knowledge base of investigation paths is future work.

Wording we will use: designed to / targets / potentially improves. Not “reduces MTTR by X%.”

16 — Same engine, stronger data plane

Future Work

We have a working core. These are extensions of the same investigation system, not a pivot.

1. Real-time integrations

Read-only Prometheus, Grafana, OpenTelemetry, Kubernetes events, GitHub/GitLab deploys, PagerDuty. Replace fixture run_probe with real queries.

2. Investigation scoring

Move from integer divergence to formal expected information gain; cost from live load; risk from blast radius — and drive selection from that, not only display it.

3. Automated evidence collection

Safe read-only diagnostic checks the engineer can approve. Still no silent writes.

4. Historical learning

Incident knowledge base, similar-incident retrieval, reuse of previous investigation paths — beyond keyword overlap.

5. Causal structure

Use the topology field that is already stored but unused; multi-factor incidents; dependency-aware probes.

6–7. Bounded experiments & evaluation

Canary only with server-side approval, hard traffic/time caps, auto-revert. Measure investigation steps, acceptance, and accuracy on a larger realistic set — not a fake MTTR slide.
